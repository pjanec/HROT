## 1. The one idea

Today an "action on an entity" is expressed **three different ways**, and the surface you are on decides
which one you get:

| Surface | How its menu is built |
|---|---|
| Entity **inspector** row | `IEntityContextMenuHandler` — hand-written lambdas, per host |
| **Map** right-click | `ContextMenuState.MenuJson` → `ContextMenuProjectorGizmo` → `DebugGizmoLayer` popup |
| **ORBAT** row | hardcoded at the ImGui call site (ExCon), or one fixed item (`SharedOrbatPanel`) |

Underneath, all three eventually reach the **same** execution seam: `GlobalActionRegistry`
(`int id → handler`) via `GlobalActionDispatchSystem`. **The execution layer is already unified. Only the
authoring and presentation of the action list is fragmented.**

> ### ⭐ The proposal: name the vocabulary once
>
> **Split the declaration from the binding.**
>
> ```
> EntityActionDescriptor { Id, Label, Icon, Group, Order }        // shared, inert data
>
> host.RegisterAction(EntityActions.Delete,                        // bound per host, at registration
>                     isApplicable: (e, ctx) => …,
>                     execute:      (e, ctx) => …);
> ```
>
> **One identity, label, icon and ordering** ⇒ a consistent menu across surfaces and modes.
> **N implementations** ⇒ the editor's networkless `Delete` and SimHost's network-aware one both stay
> correct. `GlobalActionRegistry` remains the execution backend, so the DDS int-id vocabulary is untouched.
>
> ⚠ **Revised 2026-08-10.** An earlier draft said unifying the three `Delete`s *"forces a decision about
> which behaviour is correct."* **Wrong** — the divergence is structural, and the user ruled the handlers
> legitimate. Unify the declaration only.

**Why this shape and not a new framework:** it is `IEntityContextMenuHandler` with the *declaration*
lifted out and the *binding* left where it is. That interface already exists, already works, and hosts
already use it — this extends the one seam proven here rather than inventing beside it.

> ### 🔒 The layering rule this must obey
>
> | Layer | May know |
> |---|---|
> | `Fdp.Presentation` panels (inspector, ORBAT, map popup) | the registration interface, and an **opaque context** they pass through untouched |
> | Shared descriptors | id, label, icon, group, order — **inert data, no behaviour** |
> | Subsystem composition roots | everything: which descriptors to register, with which handlers and conditions |
>
> **A generic panel must never learn what a *mode* is, nor what any action does.** `CurrentPerspective`
> may travel in the context because it is already a `Fdp.Presentation`/`WindowManager` concept; `Mode` is
> a `ClusterRunner` concept and must not appear in a generic API at all.

## 2. The staged path

Each stage stands alone and is separately shippable. **No stage leaves `ClusterRunner` broken.**

### Stage 0 — Remove the traps ⭐ *no design risk, do first*

> ⚠ **Corrected 2026-08-10.** An earlier version of this list lumped **superseded** code together with
> **half-built** code. They are not the same thing and must not share a batch: one is safe to delete, the
> other encodes a decision somebody already made.

#### A — Superseded. Safe to delete (~1,700 L)

| Item | Size | Character |
|---|--:|---|
| `Hrot.UI.Common` | 1,171 L | **An abandoned extraction.** Someone began moving shared UI into a neutral project and renamed the namespace on the *originals* to match the planned destination — then stopped. The live twin in `Hrot.Presentation` is the **newer** side (it carries an extra `vehicleId` local and reworded docs). What is left behind is the stale copy |
| ExCon `InspectorPanel` + `DataMonitorPanel` | 435 L | **Explicitly `[Obsolete]`**, doc says *"retained only for reference"*. Superseded by `DerEntityInspectorPanel`, which ExCon actually uses |
| `EditorOrbatPanel` + `EditorOrbatWindow` | ~40 L | Superseded by `EditorSharedOrbatWindow` / `SharedOrbatPanel`. Constructed at `EditorSubsystem.cs:1559`, **never registered** |
| `EntityPropertyInspector` | 48 L | Superseded by the FDP inspector. Never instantiated |

⚠ **Deleting `Hrot.UI.Common` is not a verdict on the idea it encodes.** A neutral shared-UI project may
well be the right destination — see [§1's layering rule](#1-the-one-idea). We are deleting a **stale
copy**, not rejecting the intent.

#### B — Half-built, mid-migration. 🔒 **Do NOT delete — each needs a decision**

| Item | Why it is not dead |
|---|---|
| `ScenarioEditorModule` | An explicit stub: *"populated in **PACK2-E002** (tool migration) and **PACK2-E003** (render layer migration)"*. ⚠ **PACK2-E002 is tool migration — which is exactly [Stage 4](#stage-4--tools-become-first-class).** Somebody already decided where that work should live; deleting the stub discards the decision |
| `SelectionRenderSystem` + `SelectionRenderConstants` | **Fully implemented** `IMapLayer` drawing selection rings, deliberately **moved** into `Hrot.ScenarioEditor` by the *"GZ059 legacy-layer cleanup"* — with `RenderLayerPresenceTests` asserting it stayed. No host wires it. ⚠ **Ambiguous:** either the migration's last step was never taken, or a gizmo-based highlight superseded it and the test is now stale. **Establish which before touching it** |
| `WorkspaceMenuBuilder` | A complete, documented model with **no renderer**. The repo's own report says *"Workspace submenu has no ImGui rendering yet."* A pending feature, not dead code |
| `EditorTool.Select` | `case Select: break;` — but selection genuinely works via the always-on ECS gizmo path. So the **button** is dead, the **capability** is not. Remove the button, or give it real state in [Stage 4](#stage-4--tools-become-first-class) |

**Why A goes first:** every later stage edits these files or their live twins. Doing it first means no
work is done twice, or done in the copy that never compiles.
**Gate:** build + all suites green, **zero** behaviour change.
⚠ Note `RenderLayerPresenceTests` will constrain any move of the B-list items.

### Stage 1 — Name the vocabulary *(no surface changes yet)*

- Introduce `EntityActionDescriptor` (inert data) + a registration API carrying
  `isApplicable` / `isEnabled` / `execute`, and an **opaque** `ActionContext`.
- Publish the **shared descriptors** for the items that exist everywhere — `Center`, `Select`, `Delete`,
  `Rotate` — so their id, label, icon and ordering come from one place.
- Adapt existing `IEntityContextMenuHandler` registrations behind an adapter — **behaviour identical**.
- **Each host keeps its own handler** and binds it to the shared descriptor. Nothing is deleted except
  the duplicated *labels and ordering*.

🔒 **Do NOT unify the three `Delete` handlers.** The Editor publishes `DestroyEntityCommand`; SimHost
branches on `NetworkIdentity`, falls back to `_repo.DestroyEntity`, and clears selection and inspector
state. **That divergence is correct** — the editor is networkless, the others are not (user ruling,
2026-08-10). Share the *descriptor*; each host keeps and registers its own handler.

**Gate:** Editor / SimHost / CGF menus visually **identical** before and after. Screenshot both.

### Stage 2 — One menu on every surface *(delivers the consistency requirement)*

- Map right-click and inspector row menu render from the **same provider chain**.
- 🔒 **IG's network pipeline stays out** (ruled 2026-08-10). The Editor's `JsonEntityContextMenuHandler`
  becomes a *local* provider in the unified chain; IG's `ContextMenuSystem` DDS round-trip is untouched.
  The two parsers therefore remain — accepted, because they serve different features.
- **ORBAT rows become the third surface** — which is also the ORBAT seam, so ExCon's 434-line fork can
  collapse into the shared panel. *Two problems, one mechanism.*

**Gate:** right-click the same entity on the map and in the inspector → same actions, minus any the
surface legitimately cannot offer.

### Stage 3 — Perspective enters the context

- **Two axes, each at its own layer** — **mode** is expressed by *the predicates and handlers a host
  binds* (composition time, never visible to a generic panel); **perspective** is a *condition carried by
  the registration* (runtime). Both affect the menu, as the user requires, with no concept leaking down.
  ⚠ **Revised 2026-08-10:** mode was going to be *which registrations a host performs*, but the user
  ruled the registration **set uniform** across Editor/SimHost/CGF — so mode moved into the rules. A
  third decider, **data availability** (component presence per entity), needs no mechanism: it is already
  how `[GizmoProjector]` keys and `HasComponent<T>` guards work.
- Apply the same idea to the **main menu**: give `GlobalMenuRegistry.RegisterItem` the `perspective:`
  filter that `MainToolbarManager.RegisterEntry` **already has**.
- 🔴 **Fix the perspective vocabulary bug here** — validate a restored perspective against
  `GetPerspectives()`, not against subsystem names
  ([§5b](UX_Current_UI_Architecture.md#5b-how-perspective-switching-actually-works)).

**Gate:** switch perspective → the entity menu and main menu change accordingly; quit inside a Blueprint
perspective and relaunch → you return to it.

### Stage 4 — Tools become first-class

- `ToolDescriptor { id, label, icon, activation, gizmo factory }` + a per-host **tool set**.
- Collapse the **four** activation idioms into one; remove the Editor's duplicated activation path.
- The toolbar gains active-tool state ([UXR-84](UX_Requirements.md#uxr-84)) — free once the state exists.

**Gate:** Editor and SimHost show different tool sets drawn from one pool — the mode enabling a set and
the perspective narrowing it — and the active tool is visible. ⚠ *Not* a prep-vs-live split: the Editor
runs too, so "is running" is an applicability condition, not a tool-set axis.

### Stage 4b — The layout default becomes an artifact *(user direction, 2026-08-10)*

**The problem is not where `imgui.ini` lives — it is that there is no shipped default.** The user:
*"It fails to install a good proven default for a new user. Also the whole project is under development
so the default is evolving. I would rather have one `imgui.ini` in the source tree, not per-user."*

⚠ **Do not point ImGui directly at a tracked file.** ImGui **writes** the ini on exit and periodically,
so every run by every developer would dirty a tracked file and produce merge conflicts over window
coordinates.

### The design — refined by the user, 2026-08-10

The user accepted the seed-for-new-users mechanism and added the two parts that matter:

> *"What I actually want is the option to have a main menu item to **save the current setting as the
> default**; and during the development stage (i.e. practically always now) to **auto-revert the user
> setting to the repo-committed default on each new run** — copy the default to the user folder, force
> overwriting whatever was there, so ImGui loads the user copy as usual but reset to default, and on
> exit save to the user folder as now."*

**The flow, confirmed workable against the code:**

| When | What happens |
|---|---|
| **Startup**, revert mode ON | Force-copy repo default → user path, **before** `IniFilename` is assigned (`RaylibPresentationShell.cs:128-136`). ImGui then loads the user copy exactly as it does today |
| **Startup**, revert mode OFF | Copy **only if the user file is missing** — the new-user seed |
| **During the session** | Unchanged. ImGui owns the user copy |
| **Exit** | Unchanged — ImGui writes the user copy. In revert mode it is simply discarded next run |
| **`Save Current Layout as Default`** | Copy user path → **source-tree** default, ready to commit |

⭐ **A consequence worth naming:** with revert-on-start ON, **every launch is the fresh-profile test**.
[UXR-04](UX_Requirements.md#uxr-04) (*"delete the layout profile, launch, walk the path — no window
opened manually"*) stops being an occasional audit and becomes something the team dogfoods continuously.
That is a stronger argument for this design than the convenience.

#### ⚠ The half that is missing from the plan: a layout is **two** files

| File | Holds |
|---|---|
| `imgui.ini` | docking tree, window positions and sizes |
| **`fdp_windows.json`** | which windows are **open / pinned**, UI scale, active perspective (`WindowManager.cs:368-382`) |

Reverting only `imgui.ini` yields **default docking with the user's open/closed window set** — an
inconsistent hybrid, and *"Save as default"* would capture only half the layout.

⇒ **Treat the default as a pair.** Both revert together; both are written by *Save as Default*.

#### 🔴 The read/write asymmetry — and the failure mode to avoid

**Reading** the default can use the build-output copy (`Content` + `CopyToOutputDirectory`).
**Writing** it must target the **source tree** — otherwise the commit never happens and the next build
overwrites the file.

⭐ **Use the pattern this repo already proved:** `ResolveAiBehaviorsDir` (`EditorSubsystem.cs:693-708`)
walks up from **both** `Environment.CurrentDirectory` and `AppDomain.CurrentDomain.BaseDirectory`
looking for a known relative path — with a comment recording *why* a hardcoded `../../../` was rejected
(*"fragile and breaks when the editor runs from a different bin depth"*).

🔴 **When the source tree cannot be resolved, disable the menu item — do not silently write to `bin`.**
That is [Trap #5](UX_RESUME.md#5-traps), the `default:`-returns-success shape that has killed four
features here.

#### The remaining details

| # | |
|--:|---|
| 1 | Give `SetupImGui()` a **path parameter** — the seam that must exist regardless |
| 2 | **Revert-on-start is a setting, not a rebuild** — a `[Option]` on `HrotRunnerConfiguration` beside `AiBehaviorsProjectPath`. ON during development, OFF for release |
| 3 | Name both files **per preset**, ending the editor↔`ClusterRunner` collision on one machine-wide file |
| 4 | Menu home: **`Window ▸ Layout`** — *Reset to Default* (always) · *Save Current as Default* (dev only, greyed when the source tree is unresolvable). Keeps a developer action out of the author's face, per [UXR-06](UX_Requirements.md#uxr-06) |

### Stage 5 — Camera and viewport *(independent — can run in parallel)*

One camera-setup path reading the **effective** (unoccluded) viewport. Fixes four stale copies *and* the
occlusion defect together. Needs no part of stages 1–4.

### Stage 6 — Consolidate what remains

Spawn UI (4 → 1, behind the tool and action seams) · the gizmo main-menu-bar copy-paste ×4 · `PanelConstants`.

## 6. On the word "profile" — withdrawn

Claude used "profile" loosely for *"the per-mode declaration of which windows, menu items, layers, tools
and actions are present."* **The user asked what it meant and where it lives. The honest answer is that
it should not exist as a thing.**

A profile object would be a higher-level concept that generic components must understand in order to
apply — exactly the leak ruled out on 2026-08-10.

> **The profile already exists and is not an artifact: it is the set of registrations a host performs in
> its own composition root.** Every subsystem has one today. Nothing new is needed to hold it.

⇒ The real question is not *where a profile lives* but **what a registration carries**. Today it carries
a handler; it should also carry the conditions under which the item applies — which is exactly what makes
it register-time parametrizable. That is [Q26-B](Architect_Question_26_Entity_Action_Model.md), restated.

**The word is dropped from this programme's vocabulary.**
