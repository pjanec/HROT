QUESTIONS

Q9 — Co-existence with .bp.json paths. If EQS templates can be authored as either hand-written C# classes ([EqsTemplate(AssetId = ...)]) or as .bp.json files (compiled by the source generator), what's the recommended convention for detecting and reporting AssetId collisions between the two paths? Build-time error in the source generator? Runtime error during registration? Some other facility?


Q10 — Hot-reload of hand-written C# template classes. The architect described hot-reload for the AI assembly via AssemblyLoadContext and AiHotReloadCoordinator. Hand-written C# classes live in that same AI assembly. When a designer edits a hand-written [EqsTemplate] class and saves, does the hot-reload pipeline catch the change the same way it catches .bp.json changes — i.e., MSBuild rebuilds, AiHotReloadCoordinator swaps ALCs, the registry re-scans and applies Soft/Hard reload classification? Or do hand-written templates require a full process restart?

REPLIES

Q9

Collisions between hand-written C# template classes and `.bp.json` templates are detected and reported as a runtime error during the registration phase, rather than a build-time error in the source generator. 

When templates are loaded into the engine, they are first added to a staging buffer, such as `BlueprintRegistryStaging`, which indexes them by the 32-bit integer ID derived from their `AssetId`. If the registry attempts to add a new template and detects that its ID already exists in the staging dictionary, it immediately throws an `InvalidOperationException`. This exception explicitly reports the collision by stating which new template name is attempting to replace the existing one, and advises the developer to regenerate one asset's GUID.

Because this validation occurs during the atomic staging process at runtime, the engine is able to handle the collision gracefully. If a designer introduces a collision that is compiled and picked up during a hot-reload, the `AiHotReloadCoordinator` will catch the resulting exception when it invokes the registrars. The coordinator will then safely abort the atomic commit, fire an `OnReloadFailed` event, and unload the new AssemblyLoadContext (ALC) to prevent memory leaks. The live simulation is entirely protected from the collision and will continue executing the previous, valid templates without interruption.

Q10

Hand-written C# template classes do not require a full process restart; they participate in the exact same hot-reload pipeline as `.bp.json` templates. 

Because both the hand-written C# classes and the source-generated C# code emitted from `.bp.json` files are compiled into the identical AI assembly (`Hrot.AI.Behaviors.dll`), they share the same `AssemblyLoadContext` (ALC) lifecycle. 

When a designer edits a hand-written C# class and saves the file, the hot-reload workflow operates as follows:
1.  **Recompilation:** A background MSBuild process is triggered (e.g., via the editor's `RebuildAndReloadAI` action) to recompile the assembly. 
2.  **Detection & ALC Load:** Once MSBuild overwrites the `.dll` on disk, the file-watcher inside the `AiHotReloadCoordinator` detects the change. It immediately loads the newly built assembly into a fresh, collectible ALC on a background thread and scans for registrars.
3.  **Atomic Swap & Re-Scan:** On the main thread, the coordinator clears stale pointers, invokes the registrars to stage the updated definitions, and atomically swaps the ALC. 
4.  **Soft/Hard Classification:** The exact same reload classification is applied to the hand-written C# classes. The engine's `HotReloadManager` iterates through the chunks and compares the `StructureHash` and `ParamHash` of the newly registered templates against the old ones to dynamically determine if live entities require a hard reset or seamlessly receive a soft parameter update.

Ultimately, by the time the code reaches the `AiHotReloadCoordinator`, the engine treats hand-written C# templates and visually-authored templates as completely indistinguishable.



EXTRA QUESTIONS

EQ1 - On the relationship between [EqsTemplate] and [BlueprintRegistrar]. The architect mentioned [BlueprintRegistrar] as the attribute the hot-reload coordinator looks for on generated registrar classes. For hand-written [EqsTemplate] classes, the registrar can either be: (a) the template class itself implements registration directly, or (b) a separate [BlueprintRegistrar] static class is generated by a tiny source generator that scans for [EqsTemplate] attributes and emits the registrars. Option (b) preserves the same hot-reload pattern as the JSON path. I lean (b) — it keeps the hot-reload coordinator's contract uniform.



You are completely correct to lean toward option (b); employing a tiny source generator to emit a `[BlueprintRegistrar]` static class perfectly aligns with our established architectural patterns. 

Our `AiHotReloadCoordinator` enforces a strict contract: during a reload, it explicitly scans the compiled assembly's types looking solely for the `[BlueprintRegistrarAttribute]`. When it finds a matching class, it extracts and invokes its public static `Register` or `RegisterAll` method to stage the definitions. If you were to force hand-written templates to implement registration directly (option a), developers would have to manually maintain these registration methods, or the coordinator would have to be modified to scan for multiple distinct attribute types, which would break the uniformity of the hot-reload pipeline.

Instead, option (b) mirrors exactly how we already handle C# authoring for Behavior Trees and Hierarchical State Machines. For example, our `BTreeDefinitionGenerator` acts as an incremental source generator that scans the syntax tree for methods annotated with `[BTreeDefinition]`, automatically aggregating them into a catalog. Similarly, the `HsmActionGenerator` scans for `[HsmAction]` and `[SharedAiAction]` attributes and emits a centralized `HsmActionRegistrar` class decorated with the required `[HsmActionRegistrar]` attribute.

By building a small source generator that intercepts your `[EqsTemplate]` classes and emits a single, centralized `[BlueprintRegistrar]` class containing the `RegisterAll` calls, you guarantee that both the visual `.bp.json` path and the hand-written C# path converge into the exact same registration mechanism. This keeps the `AiHotReloadCoordinator` perfectly agnostic to how the templates were originally authored, preserving its uniform contract and ensuring safe, atomic staging on the main thread.



EQ2 - On a slightly subtle point about Build()'s purity. The Build() method must be deterministic (given the same code, produces the same template, produces the same hash). It must not depend on runtime state, the current scenario, or anything mutable. This is obvious in principle but worth declaring explicitly because it's the kind of thing where someone might be tempted to write if (currentScenario.IsUrban) UseDifferentGenerator() — which would be wrong. Templates are static authoring; runtime variation is expressed through sensor parameters (the runtime parameter struct on the EqsSensor component), not by templates that look at the world.
This should be a documented rule and possibly enforced via an analyzer that flags Build() methods that read non-parameter state. Worth doing?


You are absolutely correct; the template `Build()` method must be strictly pure and deterministic. In our architecture, templates represent the immutable "ROM" definition of a behavior or query, whereas runtime and environmental variations must be managed exclusively through the "RAM"—the ECS components and blackboard parameters. 

The engine already provides a structural baseline to prevent this anti-pattern. For example, our Roslyn source generator `BTreeDefinitionGenerator` enforces via the `BTree002` diagnostic that any method defining a behavior tree must be `static` and take exactly zero parameters. By enforcing a parameterless static signature for your `[EqsTemplate]` builder methods, you inherently prevent developers from injecting transient state like an `ISimulationView` or `ScenarioContext`.

However, as you pointed out, a developer could still theoretically reach out to global static state (e.g., reading a static `currentScenario.IsUrban` flag) inside the builder. Enforcing purity via a dedicated Roslyn analyzer is highly recommended and aligns perfectly with how we already police the engine. 

We currently use the `Fdp.Toolkits.Analyzers` project to enforce domain-specific architectural constraints at compile time, such as the `BehaviorParameterSizeAnalyzer` which issues an `FDP_001` error if a behavior's parameter struct exceeds our strict memory-layout budgets. Creating a similar analyzer to scan `[EqsTemplate]` methods and flag any references to forbidden global state, singletons, or non-deterministic APIs (like `DateTime.Now`) would be a completely idiomatic and valuable addition to the pipeline.
