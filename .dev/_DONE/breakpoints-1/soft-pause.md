The "soft pause" is a non-blocking debugging mechanism introduced in the Slice 1 Blueprint debug protocol to halt the simulation when a breakpoint is hit without freezing the editor's UI.
In the FDP engine, ECS simulation (Update()) and ImGui rendering (DrawUI()) run sequentially on the same main thread. If a breakpoint were to halt execution by blocking the thread (e.g., using a WaitOne() signal), it would deadlock the entire OS window, preventing the UI from painting and making it impossible for the user to inspect variables or click "Continue".
The soft pause solves this by decoupling the breakpoint trigger from the simulation clock:
Zero-blocking Probes: When a generated Blueprint hits a breakpoint, the debug probe captures the execution state, requests a pause from the time controller, and immediately returns execution back to the engine within nanoseconds. It never blocks the calling thread.
Tick Completion: The engine is allowed to finish the remainder of the current simulation tick naturally.
Time Halting: On the next frame, the time controller halts the advancement of simulation time. Because the engine's main loop continues to spin, the editor UI remains fully responsive for state inspection and debugging, but the ECS simulation does not advance forward.
Architecturally, this is handled by the IBlueprintTimeController adapter, which wraps the engine's existing MasterSyncController. When a soft pause is requested, it calls _masterSync.SwitchToDeterministic(new HashSet<int>()), switching the master controller into lockstep mode with an empty network slave roster. This leverages the engine's existing network-sync logic to freeze the local simulation clock without touching thread locks.
The primary trade-off of this design is that we lose absolute mid-tick precision. Instead of halting execution exactly before a specific node evaluates, the pause takes effect at the frame boundary immediately following the node's execution. Step operations (Step Over, Step Into, Step Out) adapt to this by advancing the engine by exactly one 60Hz tick per step request, effectively mapping one tick to one node's worth of execution.
