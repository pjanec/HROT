# BF-04 Report: Step-past-end-of-tick lands on first node, not breakpoint

**Status:** DONE — all new tests green; 7 pre-existing reds unchanged.

## End-of-tick target logic

When `StepForwardOrCF6` reaches the end of the recording (pointer is at the last recorded node), it calls the new `StepFromNodeOrNextIteration` method instead of `StepFromNode` directly.

`StepFromNodeOrNextIteration(assetId, graphId, lastNodeId, fallback)` distinguishes two cases:

1. **Non-terminal last node** (`allTerminal == false`): the last recorded node has at least one non-terminal exec-successor. Delegates to the existing `StepFromNode` (BF-03 path) — sets a temp BP on the successor and calls `RequestResume()`.

2. **Terminal last node** (`allTerminal == true`): all exec-successors of the last recorded node are terminal (e.g. `Delay → Return`). This means the tick ends with no further executable node in the current iteration. BF-04 path: find the graph's first executable node(s) and set temp BPs on them, then `RequestResume()`.

`allTerminal` is computed as:
```csharp
bool allTerminal = successors.Count == 0 ||
                   successors.All(s => ExecSuccessors.GetSuccessors(graph, s).Count == 0);
```

## First-node temp BP computation

```csharp
var entryNode = graph.Nodes.OfType<EventEntryNode>().FirstOrDefault();
// fallback to Continue() if graph has no entry node
var entrySuccessors = ExecSuccessors.GetSuccessors(graph, entryNode.Id);
var firstNodes = entrySuccessors
    .Where(s => ExecSuccessors.GetSuccessors(graph, s).Count > 0)
    .ToList();
// fallback to Continue() if no non-terminal entry successors found
var targets = firstNodes.Select(s => new BreakpointTarget(assetId, graphId, s));
SetTemporaryBreakpoints(targets);
```

`SetTemporaryBreakpoints` translates authored node IDs to probe IDs via `ResolveProbeId` (DebugMap if present, otherwise `nodeId.ToString("D")`) — the same path used by CF-6 stepping. The existing user-BP suppression (temp BPs suppress user BPs) ensures the session lands on the first node, not the user BP, even when both probes fire in the same tick.

## Instance blueprint timing note

For `Delay → Return` (terminal): the Delay state machine (generated by `WaitLowering_Instance`) processes the elapsed delay and executes the resume block (`Return`) in one tick (Frame N+1), then resets `cursor = 0`. The blueprint DOES NOT re-run from Entry within Frame N+1. It re-runs from Entry in Frame N+2. This requires two TickFrames after the bridge:
- Frame N+1: Delay elapses → Return (no probe) → cursor reset. Session NOT paused. Temp BP still armed.
- Frame N+2: Entry → Block A (seqId probe) → temp BP fires → PAUSE on first node.

This is different from the `Delay → SetVar → Return` case (BF-03 / Test 6) where the SetVar resume block fires in Frame N+1 directly.

## Discriminating test (Test 8) — exact landing node asserted

**Test:** `TickBridge_StepPastEndOfTick_LandsOnFirstNode_NotBreakpoint`

Graph: `Entry → Sequence(seqId = first node) → Then0: SetVar(svId = BP node, no exec-out link, falls through) → Then1: Delay(delayId) → Return`

- BP on `svId` (mid-chain, NOT the first node)
- Recorded on Tick 1: `[seqId, svId, delayId]` (recording continues while paused; Block C fires before suspend)
- Pointer advanced to `delayId` (last recorded, index 2)
- Bridge called: `GetSuccessors(delayId) = [retId]`, `GetSuccessors(retId) = []` → `allTerminal = true` → entry's successor `seqId` gets temp BP
- Frame N+1: Delay elapses → Return (no probe) → NOT paused, temp BP still armed
- Frame N+2: Block A fires (seqId probe) → temp BP fires → PAUSED at `seqId`

**Critical assertion:**
```csharp
Assert.True(landingNodeId == seqId.ToString("D"),
    $"BF-04: landing node must be seqId (first node), got {landingNodeId}.");
Assert.True(landingNodeId != svId.ToString("D"),
    "BF-04 discriminating assertion: landing must NOT be the BP node.");
```

This assertion was absent in BF-03. With BF-03's `Continue()` fallback, the old code would have landed on `svId` (the user BP), not `seqId`.
