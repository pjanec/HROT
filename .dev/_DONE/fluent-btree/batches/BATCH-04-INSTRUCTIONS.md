#### Step 1.2: Implement BTreeActionGenerator

**File:** `FDP/ExtDeps/FastBTree/src/Fbt.SourceGen/BTreeActionGenerator.cs`

Implement `BTreeActionGenerator : IIncrementalGenerator` that:

1. **Scans** for methods annotated with `[BTreeAction]` or `[BTreeCondition]` (by attribute class name `"BTreeActionAttribute"` or `"BTreeConditionAttribute"`)
2. **Detects delegate type** from method signature:
   - **Simple delegate**: method signature matches `(ref TBlackboard, ref BehaviorTreeState, ref TContext, int)` — 4 parameters. Register directly with `registry.Register("MethodName", DeclaringType.MethodName)`.
   - **Reusable delegate**: method signature matches `(ref TValue, ref BehaviorTreeState, ref TContext)` — 3 parameters. This requires knowing the blackboard type and field offset, which is not knowable from the method signature alone at source generation time. **For this batch: skip reusable delegates (3-param) in the generator. Emit a comment explaining they must be registered via BTreeBuilder expression binding instead. Note this limitation in your report as a known gap (FBT-011 only handles 4-param NodeLogicDelegate methods in this batch).** A future enhancement could add `[BTreeAction(BlackboardType=typeof(MyBB), FieldName="AmmoCount")]` attribute fields.
3. **Emits** `FbtActionRegistrar.g.cs` in namespace `{AssemblyName}.Generated`:
   ```csharp
   // <auto-generated/>
   using System.Runtime.CompilerServices;
   using Fbt;
   using Fbt.Runtime;

   namespace {AssemblyName}.Generated
   {
       [FbtRegistrar]
       public static class FbtActionRegistrar
       {
           public static void RegisterAll<TBlackboard, TContext>(
               ActionRegistry<TBlackboard, TContext> registry)
               where TBlackboard : unmanaged
               where TContext : struct
           {
               // NOTE: Only NodeLogicDelegate (4-param) methods are registered here.
               // Reusable delegates (3-param) must be registered via BTreeBuilder
               // expression binding or a manually written RegisterAll override.
               registry.Register(nameof({DeclaringType}.{MethodName}), {DeclaringType}.{MethodName});
               // ... one line per found [BTreeAction] / [BTreeCondition] method
           }
       }
   }
   ```
4. **Diagnostic:** Emit Roslyn diagnostic `BTreeDiag001` (Warning, not error) if a 3-param `[BTreeAction]`/`[BTreeCondition]` method is found and skipped. Message: `"BTreeAction '{0}' is a reusable delegate (3 parameters). Register it via BTreeBuilder expression binding."` Use `DiagnosticSeverity.Warning`.
5. **Skips** if no `[BTreeAction]` / `[BTreeCondition]` methods found in the assembly — do NOT emit an empty registrar.

**Key implementation notes:**
- Use `IIncrementalGenerator`, not `ISourceGenerator` (like FastHSM does — FastHSM's `HsmActionGenerator` is already `IIncrementalGenerator`, so follow it exactly)
- Predicate: `node is MethodDeclarationSyntax method && method.AttributeLists.Count > 0`
- Transform: get symbol, check for `BTreeActionAttribute` or `BTreeConditionAttribute`, return `MethodInfo` record
- Count parameters in the method's `Parameters` list from the symbol to determine delegate type (3 vs 4 params)
- Use `symbol.ContainingType.ToDisplayString()` for the declaring type name in the generated `Register` call

**`BTreeDiag001` descriptor:**
```csharp
private static readonly DiagnosticDescriptor ReusableDelegateSkipped = new DiagnosticDescriptor(
    id: "BTree001",
    title: "Reusable BTree delegate skipped",
    messageFormat: "BTreeAction '{0}' is a reusable delegate (3 parameters). Register it via BTreeBuilder expression binding.",
    category: "BTreeSourceGen",
    defaultSeverity: DiagnosticSeverity.Warning,
    isEnabledByDefault: true);
```

### Task 2: FbtAutoDiscovery (FBT-013)

**File:** `FDP/ExtDeps/FastBTree/src/Fbt.Compiler/FbtAutoDiscovery.cs`

```csharp
using System;
using System.Reflection;
using Fbt.Runtime;

namespace Fbt.Compiler
{
    /// <summary>
    /// Scans all loaded assemblies for types annotated with <see cref="FbtRegistrarAttribute"/>
    /// and invokes their <c>RegisterAll</c> method.
    /// </summary>
    public static class FbtAutoDiscovery
    {
        /// <summary>
        /// Scans <see cref="AppDomain.CurrentDomain"/> assemblies for <c>[FbtRegistrar]</c>-annotated
        /// types and invokes <c>RegisterAll(registry)</c> via reflection on each.
        /// Non-reflectable assemblies are silently skipped.
        /// </summary>
        public static void ScanAndRegister<TBlackboard, TContext>(
            ActionRegistry<TBlackboard, TContext> registry)
            where TBlackboard : unmanaged
            where TContext : struct
        {
            foreach (var assembly in AppDomain.CurrentDomain.GetAssemblies())
            {
                try
                {
                    foreach (var type in assembly.GetTypes())
                    {
                        if (!type.IsDefined(typeof(FbtRegistrarAttribute), false))
                            continue;

                        var method = type.GetMethod(
                            "RegisterAll",
                            BindingFlags.Public | BindingFlags.Static);

                        if (method == null)
                            continue;

                        try
                        {
                            method.Invoke(null, new object[] { registry });
                        }
                        catch
                        {
                            // Skip registrars that fail (type mismatch for TBlackboard/TContext)
                        }
                    }
                }
                catch
                {
                    // Skip non-reflectable assemblies (COM, dynamic, etc.)
                }
            }
        }
    }
}
```

## 🧪 Testing Requirements

### Testing the Source Generator (FBT-011)

Source generators cannot be tested by simply writing xUnit tests that call generator code — the generator only runs during Roslyn compilation. There are two approaches:

**Approach A (Preferred for this batch): Verify generated output via compilation**

Use `Microsoft.CodeAnalysis.CSharp` (which is already referenced by the test project transitively through the generator) to create a test compilation and run the generator:

```csharp
// Approach A: compile a small C# snippet, run the generator, check the generated source
using Microsoft.CodeAnalysis;
using Microsoft.CodeAnalysis.CSharp;
...

var source = """
    using Fbt;
    using Fbt.Runtime;
    public class MyActions
    {
        [BTreeAction]
        public static NodeStatus MyAction(ref int bb, ref BehaviorTreeState s, ref object ctx, int p)
            => NodeStatus.Success;
    }
""";
// Create compilation, add generator, run, inspect generated source
```

However, this requires that the test project has `Microsoft.CodeAnalysis.CSharp` in scope. Instead of that complexity:

**Approach B (Simpler): Integration test via auto-discovery**

1. Add `[BTreeAction]` annotations to the existing `MockActions` or a new `TestActions` class in the test project (4-param signature)
2. The generator will run on the test project and emit `FbtActionRegistrar.g.cs`
3. Verify the generated registrar by calling `FbtAutoDiscovery.ScanAndRegister` and checking that the action is found in the registry

This approach tests both FBT-011 and FBT-013 together.

**Use Approach B** — it tests the actual generator output without requiring CodeAnalysis tooling.

**New test file:** `FDP/ExtDeps/FastBTree/tests/Fbt.Tests/Unit/AutoDiscoveryTests.cs`

## ⚠️ Common Pitfalls

- `netstandard2.0` is required for Roslyn generators — the generator project must NOT target `net8.0`
- The generator does NOT reference `Fbt.Kernel` — it works entirely through Roslyn's semantic model and string generation. Attribute names are matched by string ("BTreeActionAttribute"), not by type reference.
- When adding the generator as an analyzer reference to Fbt.Tests.csproj, use `OutputItemType="Analyzer" ReferenceOutputAssembly="false"` to prevent the generator assembly from appearing as a runtime reference.
- If `AnnotatedTestActions` is in the test project, the generator WILL run on it and try to emit a registrar. The test project must build cleanly with the generated code present.
- `ActionRegistry<TBlackboard, TContext>` — check if it's accessible from generated code (it's in `Fbt.Runtime` namespace, which must be imported in the generated file).
- The generated `RegisterAll` method is generic (`<TBlackboard, TContext>`), but delegates are typed — the generated `registry.Register(...)` call may have type inference issues if the method parameter types don't exactly match `NodeLogicDelegate<TBlackboard, TContext>`. Verify by actually building the test project after wiring up the generator.
