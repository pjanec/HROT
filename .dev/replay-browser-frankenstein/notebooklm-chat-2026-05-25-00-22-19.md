They project AAA-style execution pauses onto our ECS data-breakpoint architecture without injecting blocking synchronization primitives into the AI kernels.

**Data Access and Retrieval** The evaluation relies on the `BTreeTraceWorkingMemory1024` component, a 1024-byte unmanaged ring buffer attached to the entity. During the simulation phase, the FastBTree `Interpreter` invokes the `ITreeTracer` interface on the stack-allocated `BTreeContext`. This writes tightly packed 16-byte `BTreeTraceRecord` structures directly into the component's memory. The condition engine accesses this specific buffer during the post-simulation phase to reconstruct the chronological execution flow of the tree.

**User Definition** The developer defines the breakpoint by selecting a target node in the editor UI and specifying the lifecycle phase to trap. This UI intent translates into a standard predicate definition targeting the `BTreeTraceRecord` fields:

-   **On Node Activation (On Enter):** The user targets a specific node execution start. The predicate checks for `OpCode == BTreeTraceOpCode.NodeEvaluated` where the `Status` is either `NodeStatus.Success` or `NodeStatus.Failure`.-   **On Abort / Interruption:** The user targets branch invalidation. The predicate checks for `OpCode == BTreeTraceOpCode.ScopePopped` (indicating the execution stack was unwound) or `OpCode == BTreeTraceOpCode.ChannelMutated`.

**Compilation and Execution Pipeline** The `IPredicateCompiler` translates the definition into a zero-allocation `Func<EntityRepository, Entity, bool>` delegate. The engine executes this delegate using `QueryDelta` to skip unmodified 64KB chunks, ensuring we only evaluate entities whose trace buffers actually changed during the tick. The JIT-compiled IL iterates over the `BTreeTraceWorkingMemory1024.Buffer` array, matching the target `NodeIndex` and `OpCode` against the 63 available slots without boxing the records.

**Architectural Use Cases and The Rewind** Because the FDP engine enforces a strict parallel-execution model, we do not physically block the thread mid-tick the moment a B-Tree node initializes. When the trace-buffer predicate evaluates to true at the end of the tick, the debugging orchestrator executes the forward-snapshot rewind, swapping the UI's simulation view to the `_preTickSnapshot`.

This guarantees absolute determinism. The developer observes the ECS state exactly as it existed before the AI logic executed, inspecting the variables that caused the condition to flip. This perfectly mimics the standard "pause on enter" experience found in blocking architectures, but keeps the 60Hz production frame budget entirely decoupled from the debugging tools.

pls detail 6. Dynamic Partition Memory Breakpoints

Dynamic Partition Memory Breakpoints evaluate state variables within Blueprint instances, overcoming the absence of static memory offsets inherent to the engine's dynamic partition allocator.

**Data Access and Retrieval** Blueprint state is housed in tiered unmanaged components (`BlueprintBlackboard1024`, `BlueprintBlackboard4096`, `BlueprintBlackboard16384`). The memory layout of these components begins with a 32-byte `BlueprintBlackboardHeader`, followed by a dense table of 16-byte `BlueprintSlotEntry` structs. Because an entity can stack multiple Blueprint instances within a single component, data locations are strictly dynamic. To access a specific instance's memory, the system must iterate the slot table to match a specific `BlueprintId` and extract the assigned `PayloadOffset`.

**User Definition** The developer defines the breakpoint by selecting a Blueprint variable in the editor UI and applying a logical condition (e.g., `AmmoCount == 0`). The UI translates this intent into a predicate definition that stores the target tier component type, the `BlueprintId`, the variable's relative byte offset within the Blueprint's struct layout, and the threshold criteria.

**Compilation and Execution Pipeline** Because the `PayloadOffset` can shift at runtime due to tier upgrades or potential partition defragmentation, a static offset check would read corrupted memory.

To maintain the zero-allocation hot path, the `IPredicateCompiler` emits an Intermediate Language (IL) delegate that executes the partition lookup inline. During the `PostSimulation` delta query, the delegate executes the following sequence:

-   It fetches a `ref readonly` pointer to the tier component via `repo.GetComponentRO<T>`.-   It reads the `SlotCount` from the 32-byte header.-   It executes a cache-friendly linear scan over the 16-byte `BlueprintSlotEntry` array to match the stored `BlueprintId`.-   If the ID is not found, the delegate safely short-circuits and returns false.-   If found, the delegate calculates the absolute memory address by adding the `PayloadOffset` to the variable's relative offset.-   It uses `Unsafe.AsRef` to project that exact memory slice into the target primitive type and evaluates the condition.

**Architectural Use Cases and The Rewind** This mechanism is explicitly designed to handle the complexity of Blueprint memory without compromising the 60Hz deterministic constraints. It guarantees that developers can place breakpoints on highly volatile, dynamically allocated AI or logic variables safely.

When the JIT-compiled delegate evaluates to true at the tick boundary, the debugging orchestrator executes the standard forward-snapshot rewind. The editor's inspection context is repointed to the `_preTickSnapshot`, presenting the developer with the exact, unmutated state of the Blueprint instance immediately before the execution frame advanced.

what about the underlying memory data models and apis describing all these types?

The underlying memory data models for the universal breakpoint system rely on a strictly decoupled, polymorphic Data Transfer Object (DTO) hierarchy. This architecture ensures the presentation layer remains completely agnostic to the JIT compilation and ECS memory evaluation layers, serializing complex condition trees directly to JSON without custom parsing logic.

**The Polymorphic Base Contract** The root of the hierarchy is the abstract `SearchPredicateDto`. It leverages `[JsonPolymorphic]` and `[JsonDerivedType]` attributes to map JSON payloads directly to specific evaluation shapes such as `PropertyMatch`, `TransientEvent`, and `Compound`.

**Value and Composition Models**

-   **CompoundPredicateDto**: Aggregates conditions into a recursive evaluation tree using a `LogicalOperator` (`And`, `Or`) and a `List<SearchPredicateDto>` collection.-   **SearchPredicateValueDto**: The abstract base for scalar evaluations.-   **NumericPredicateDto**: Defines `MinValue` and `MaxValue` (as `double`) for bounded or exact numeric threshold checks.-   **StringPredicateDto**: Defines `Substring`, `StartsWith`, and `ExactMatch` boolean constraints for string evaluation.

**ECS Memory and Structural Models**

-   **PropertyMatchDto**: Targets standard ECS chunk data. It stores the `ComponentType`, a `PropertyPath` string representing the structural dot-notation layout, a `SearchOperator`, and a nested `Predicate` (typically a numeric or string DTO) for the threshold check.-   **StructuralPredicateDto**: Traps archetype mutations at the ECS level. It defines the `ComponentType`, the `StructuralModification` (`Added`, `Removed`, `AnyChange`), and critically, an `AuthorityRequirement` (`RequireAuthority`, `RequireGhost`, `AnyAuthority`) to filter network-replicated phantom state.-   **LifecyclePredicateDto**: Tracks entity birth and death. It defines the `EntityIdentifierType` (`EcsHandle`, `NetworkId`, `NameSubstring`), the `TargetValue` criteria, and an optional `NameComponentType` and `NamePropertyPath` to instruct the evaluator on where to extract the string identifier.

```
private unsafe void DrainPendingMutations(EntityRepository repo)
{
    if (_pendingMutations.Count == 0) return;

    var ecb = ((ISimulationView)repo).GetCommandBuffer();

    while (_pendingMutations.TryDequeue(out var mutation))
    {
        if (mutation.IsManaged)
        {
            // Tier 2: Managed references are passed directly into the ECB array.
            ecb.SetManagedComponentRaw(mutation.Target, mutation.ComponentTypeId, mutation.Payload);
        }
        else
        {
            // Tier 1: Unmanaged boxed structs must be pinned. 
            // We extract the pointer and copy the exact byte length into the ECB command stream.
            GCHandle handle = GCHandle.Alloc(mutation.Payload, GCHandleType.Pinned);
            try
            {
                void* ptr = (void*)handle.AddrOfPinnedObject();
                ecb.SetComponentRaw(mutation.Target, mutation.ComponentTypeId, ptr, mutation.SizeBytes);
            }
            finally
            {
                handle.Free();
            }
        }
    }
}
```

-   When the operator requests a step or resume, the engine restores the exact post-tick state via a byte-for-byte unmanaged copy using `_liveRepo.SyncFrom(_postTickSnapshot)`.-   The queued edits are then drained directly into the `EntityCommandBuffer`.-   The simulation clock is instructed to advance one tick, allowing the standard ECB write path to apply the mutations at the exact boundary of tick N+1.

Architecturally, accepting this 1-tick latency trade-off completely eliminates the need for a resimulation path. The engine avoids executing any replay logic, `EventAccumulator` injection, or physics rewinds, effectively neutralizing the desynchronization risks associated with re-running logic over components marked with `DataPolicy.NoRecord` or `DataPolicy.NoSnapshot`.

Crucially, this design preserves linear invariance for the Flight Recorder. Tick N is simulated and recorded naturally before the pause evaluates and halts time. Because the engine never recalculates the historical frame, the recorder sees no duplicate frames and requires no write-head rollback. The deferred edits simply appear as standard structural writes captured natively in the delta between tick N and tick N+1.

detail 5. **Linear Flight Recorder Invariance:**

Linear Flight Recorder Invariance ensures that the `.fdp` recording process remains entirely oblivious to the debugger's time-travel and pause operations, producing a perfectly linear sequence of frames without requiring complex write-head rollbacks.

The architectural mechanism achieving this relies on the forward snapshot pattern avoiding resimulation. The `AsyncRecorder` and `RecorderTickSystem` execute during `SystemPhase.PostSimulation`, naturally capturing the state of Tick N before the universal breakpoint evaluation triggers the soft pause and time halts.

Because the debugger avoids resimulating Tick N to step forward, it prevents the `RecorderTickSystem` from capturing Tick N a second time, which would otherwise corrupt the delta stream with duplicate frames. When the user resumes execution, the clean step simply restores the `_postTickSnapshot` (which is identical to what was already recorded) and advances the clock to Tick N+1. From the perspective of the flight recorder, the chronology is perfectly linear: Tick N concludes, time stops, and eventually Tick N+1 simulates.

Furthermore, any live state edits applied via the deferred mutation contract are executed as standard `EntityCommandBuffer` writes at the boundary of Tick N+1. The recorder captures these as a normal delta between Tick N and Tick N+1, precisely as if an internal engine system had requested the mutation.

detail 7. **Torn-State Exception Interception:**

Torn-State Exception Interception guarantees that mid-tick unhandled exceptions do not destroy the forensic evidence required to debug them. Normal universal breakpoints evaluate at the phase boundary via chunk delta queries, which is fundamentally too late if a module crashes mid-execution.

When an exception occurs during `ModuleHostKernel.ExecuteModuleSafe`, the ECS memory is left in a torn state—some component arrays have been mutated by the executing systems, while others have not. By default, the kernel catches this fault, records a failure in the `ModuleCircuitBreaker`, and abandons the task.

To satisfy this success condition, the architecture must insert a diagnostic trap directly into the kernel's fault handler.

**1\. Mid-Phase Interception and Snapshotting** Upon catching the exception, before the kernel releases the `ISimulationView` or unwinds the execution state, the breakpoint orchestrator intercepts the fault. It instantly executes `_postTickSnapshot.SyncFrom(_liveRepo)`. This unmanaged memory copy securely backs up the exact corrupted chunk memory (the torn state) and invalid variable offsets precisely as they existed at the moment of the crash.

**2\. Command Buffer Quarantine** Any structural mutations queued prior to the crash sit in the thread-local `EntityCommandBuffer`. To prevent this torn logic from poisoning the rest of the frame or corrupting the global ECS state, the orchestrator clears the command buffer without executing playback.

**3\. Deterministic Rewind** The orchestrator then safely rewinds the live world by executing `_liveRepo.SyncFrom(_preTickSnapshot)`, instantly restoring the clean, deterministic state from the beginning of the frame, and halts the time controller.

**Validation of Success:** Integration of this specific condition is successful when:

-   An exception thrown inside a module cleanly soft-pauses the simulation instead of crashing the `ClusterRunner` process or initiating an automatic `ModuleCircuitBreaker` shutdown sequence.-   The presentation layer allows the developer to toggle the inspector view between the safe `_preTickSnapshot` and the torn `_postTickSnapshot` to explicitly isolate the corrupted memory layout that caused the hardware fault.

detail 8. **Open-Closed Decoupling via Polymorphic DTOs:**

The Open-Closed Principle (OCP) dictates that software entities should be open for extension but closed for modification. In the Universal Breakpoint system, this is achieved by strictly decoupling the presentation and orchestration layers from the underlying memory evaluation logic using polymorphic Data Transfer Objects (DTOs).

The orchestrator and the `DataBreakpointSystem` then mount and execute these compiled delegates blindly. They execute the logic without needing to know whether they are evaluating a spatial query, an event payload, or a Blueprint node cursor.

3\. Guaranteeing Extensibility

This design guarantees that adding a new category of breakpoint requires zero modifications to the core execution loop.

-   Define a new `SpatialBoundingPredicateDto` extending `SearchPredicateDto`.-   Add a new translation branch inside the `IPredicateCompiler` to generate the segment-intersection math.

detail 9. **Hot-Reload Memory Resiliency:**

Success Condition 9 dictates that the debugging architecture must remain absolutely memory-safe across runtime assembly swaps.

The Universal Breakpoint system relies on the `IPredicateCompiler` to translate layout-agnostic `SearchPredicateDto` configurations into highly optimized `Func<EntityRepository, Entity, bool>` delegates. These JIT-compiled delegates execute directly against unmanaged ECS chunk memory to evaluate conditions without allocations. However, when the `AiHotReloadCoordinator` loads rebuilt C# logic into a new `AssemblyLoadContext`, the underlying memory layouts of the components may shift, resulting in a changed `StructureHash`. Retaining the previously compiled delegates across this boundary creates a severe memory safety risk, as they would execute pointer arithmetic against stale byte offsets.

To achieve Hot-Reload Memory Resiliency, the architecture enforces a strict invalidation and recompilation pipeline:

**1\. Delegate Invalidation** The breakpoint orchestrator subscribes to the hot-reload lifecycle, specifically the `OnReloadCompleted` event. When a reload concludes, the manager instantly flushes the `DataBreakpointSystem`, aggressively discarding all active JIT-compiled evaluation delegates to guarantee no stale unmanaged pointers are executed against the new memory chunks.

**2\. Polymorphic Recompilation** Because the system stores the developer's intent entirely within the polymorphic `SearchPredicateDto` payload, the orchestrator simply feeds these original, type-erased DTOs back into the `IPredicateCompiler`.

**3\. Graceful Degradation** If the new assembly maintains structural compatibility with the predicate's property paths, the compiler yields a new, memory-safe delegate mapped to the updated offsets, and the orchestrator seamlessly remounts it. If the developer drastically altered the schema (e.g., removing or renaming a field targeted by a breakpoint), the compilation gracefully fails. The breakpoint is marked invalid in the UI, avoiding a silent memory access violation.

**Validation of Success:** Integration of this specific condition is successful when:

-   Triggering a hard structural hot reload while data breakpoints are active never causes an access violation or crashes the engine's `ClusterRunner` process.-   Breakpoints and watch panel expressions automatically rebind and resume scanning memory immediately after a structure-compatible hot reload completes.
