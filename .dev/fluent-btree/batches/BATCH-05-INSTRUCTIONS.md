## ✅ Tasks

### Task 1: BTreeDefinitionGenerator (FBT-012)

**Context:** The TASK-DETAIL.md spec for FBT-012 requires statically evaluating the `BTreeBuilder` call chain at compile time via Roslyn's Semantic Model and emitting pre-built `BehaviorTreeBlob` data. This is extremely complex and NOT required in this batch. **Use the pragmatic implementation described below instead.**

#### Pragmatic Implementation (APPROVED)

The `BTreeDefinitionGenerator` in this batch will:
1. Find methods annotated with `[BTreeDefinition("TreeName")]`
2. Emit `FbtTreeCatalog.g.cs` with a **lazy static cache** approach:
   - A `static Lazy<BehaviorTreeBlob>` field per tree, initialized by calling the annotated method once on first access via a `[ModuleInitializer]`.
   - Wait: `[ModuleInitializer]` will call it at startup. Use `Lazy<T>` initialized on first access to defer cost slightly.
   - **Actually: emit a `static BehaviorTreeBlob? _treeName_blob = null;` field and a `Get{TreeName}()` method that checks the field, calls the annotated method if null, caches and returns. Thread safety: use `Interlocked.CompareExchange` or simply accept single-threaded startup.**
   - Simplest correct approach: use `Lazy<BehaviorTreeBlob>`:
   ```csharp
   private static readonly Lazy<BehaviorTreeBlob> _ambush_BT_lazy =
       new Lazy<BehaviorTreeBlob>(() => BuildAmbushTree().Compile("Ambush_BT"));

   public static BehaviorTreeBlob GetAmbush_BT() => _ambush_BT_lazy.Value;
   ```
   - But wait: the annotated method is `[BTreeDefinition("Ambush_BT")]` on the method `BuildAmbushTree()` which returns what? Either:
     - `BehaviorTreeBlob` directly (method calls builder and compiles internally), OR
     - `BTreeBuilder<TBlackboard, TContext>` and the generator calls `.Compile(treeName)` on it
   - Looking at the spec: "Emit FbtTreeCatalog.g.cs with static Get{TreeName}() methods returning BehaviorTreeBlob"
   - The annotated method is the builder factory. The generator must call it and compile. But if the annotated method returns `BehaviorTreeBlob` already, the generator can call it directly.
   - **Decision for this batch:** the `[BTreeDefinition]` annotation goes on a method that returns `BehaviorTreeBlob`. The generator emits:
     ```csharp
     public static BehaviorTreeBlob GetAmbush_BT()
         => Fbt.Tests.TestFixtures.SampleTrees.BuildAmbushTree();
     ```
     i.e., it just provides a discoverable static entry point. The method itself already returns the compiled blob. This is the minimum useful version and avoids the Roslyn evaluation complexity entirely.
   - **Note this deviation in your report.** Record as DT-005 in the debt tracker.

3. **Emitted class:** `FbtTreeCatalog.g.cs` in namespace `{AssemblyName}.Generated`:
   ```csharp
   // <auto-generated/>
   using Fbt;

   namespace {AssemblyName}.Generated
   {
       public static class FbtTreeCatalog
       {
           public static BehaviorTreeBlob Get{TreeName}()
               => {DeclaringType}.{MethodName}();
       }
   }
   ```
   Where `TreeName` comes from the `BTreeDefinitionAttribute.TreeName` constructor argument, sanitized (replace spaces/special chars with `_`).

4. **Multiple methods:** If multiple `[BTreeDefinition(...)]` methods are found, emit all of them as separate `Get...()` methods in the same `FbtTreeCatalog` class.

5. **No methods found:** Do NOT emit `FbtTreeCatalog.g.cs` if no `[BTreeDefinition]` methods exist.

6. **Method signature validation:** The annotated method must:
   - Be `static`
   - Return `BehaviorTreeBlob` (check return type name)
   - Have zero parameters (it's a factory method)
   - Emit `BTreeDiag002` Warning if a `[BTreeDefinition]` method does not meet these constraints and skip it.

**Diagnostic `BTreeDiag002`:**
```csharp
private static readonly DiagnosticDescriptor InvalidDefinitionMethod = new DiagnosticDescriptor(
    id: "BTree002",
    title: "Invalid BTreeDefinition method",
    messageFormat: "Method '{0}' annotated with [BTreeDefinition] must be static, return BehaviorTreeBlob, and have no parameters.",
    category: "BTreeSourceGen",
    defaultSeverity: DiagnosticSeverity.Warning,
    isEnabledByDefault: true);
```

#### Implementation Location

Add `BTreeDefinitionGenerator` as a second generator class in the same `Fbt.SourceGen` project, or add it as a new file `BTreeDefinitionGenerator.cs`. Either approach works. Using a separate file is preferred.

## ⚠️ Common Pitfalls

- The `BTreeDefinitionAttribute` constructor argument (the tree name string) must be extracted from the Roslyn `AttributeData.ConstructorArguments[0].Value as string`. Check for null.
- Tree names may contain spaces or hyphens — sanitize to valid C# identifiers by replacing non-`[a-zA-Z0-9_]` chars with `_` for the method name.
- The generated `Get{TreeName}()` method must call `{FullyQualifiedTypeName}.{MethodName}()` — use `symbol.ContainingType.ToDisplayString()` for the type name.
- If `[BTreeDefinition]` is on a method that returns `BTreeBuilder<T>` (not `BehaviorTreeBlob`), the generator cannot call `.Compile()` from emitted code without knowing `treeName` and type params. This is why we require the annotated method to return `BehaviorTreeBlob` directly — the developer calls `.Compile(...)` inside the method body.
- Two generators in the same project: both must be registered with `[Generator]`. Ensure both classes have the attribute.
