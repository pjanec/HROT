## Implementation Details

### ANC-P5-04: Look-At Nodes (3 structs)

All look-at nodes use `[StructLayout(LayoutKind.Sequential)]` for safe memory marshaling in Blueprint codegen.

#### `LookAtPointNode`
```csharp
public struct LookAtPointNode {
    public uint TargetCharacter;      // Entity to control aim
    public float TargetPointX;        // Point in world space
    public float TargetPointY;
    public float TargetPointZ;
    public float BlendInTime;         // Blend-in duration (seconds)
    public byte Priority;             // Execution priority (0-255)
}
```
- **Purpose**: Aim a character's look-at channel toward a world-space point
- **Integration**: Executor receives TargetCharacter ID, animates lookDirection toward (X,Y,Z) over BlendInTime
- **Cross-subsystem**: Reusable in BTree, HSM, Blueprint Instance contexts via dispatcher pattern

#### `LookAtEntityNode`  
```csharp
public struct LookAtEntityNode {
    public uint TargetCharacter;      // Entity to control aim
    public uint TargetEntity;         // Entity to aim at
    public float OffsetFromTargetX;   // Offset from target position
    public float OffsetFromTargetY;
    public float OffsetFromTargetZ;
    public float BlendInTime;         // Blend-in duration (seconds)
    public byte Priority;             // Execution priority (0-255)
}
```
- **Purpose**: Aim toward another character with optional offset
- **Offset Pattern**: Common in cover systems (e.g., +0.5Y for head height, -0.1X for side angle)
- **Integration**: Executor resolves TargetEntity→position, adds offset, aims LookAtChannel

#### `ReleaseLookNode`
```csharp
public struct ReleaseLookNode {
    public uint TargetCharacter;      // Entity to release aim
    public float BlendOutTime;        // Blend-out duration (seconds)
}
```
- **Purpose**: Stop aiming, return to neutral (body-forward) orientation
- **BlendOut**: Smooth transition over duration seconds (prevents snap)

### ANC-P5-05: Getter Nodes (2 structs)

Read-only nodes that expose component state through Blueprint output ports.

#### `GetMontageQueueProgressNode`
```csharp
public struct GetMontageQueueProgressNode {
    public uint TargetCharacter;      // Entity to query queue state
}
```
- **Output Ports** (generated by compiler):
  - `CurrentEntryIndex: uint` — Index of currently-playing montage (0xFF if empty)
  - `ElapsedSeconds: float` — Seconds elapsed in current entry
  - `TotalCount: uint` — Total entries queued
- **Use Case**: Conditional branching (e.g., "if queue empty, play fallback animation")
- **No Mutation**: Read-only snapshot from AnimationMontageQueueState

#### `GetCurrentStanceNode`
```csharp
public struct GetCurrentStanceNode {
    public uint TargetCharacter;      // Entity to query stance
}
```
- **Output Ports** (generated by compiler):
  - `CurrentStance: uint` — StanceId (Standing, Crouched, Prone)
  - `BlendWeight: float` — Transition progress (0.0–1.0, 1.0=settled)
- **Use Case**: Stance-dependent behavior (e.g., "if crouched, play crouch-specific animation")
- **Transition Awareness**: Includes blend progress for smooth reactions

### ANC-P5-06: Validation Rules (ANIM008–ANIM011)

#### ANIM008: Enqueue without PlayMontageChain
**Rule:** EnqueueMontageNode used without PlayMontageChainNode in graph → **WARNING**  
**Rationale:** EnqueueMontageNode only appends to queue; PlayMontageChainNode executes the queue. Using EnqueueMontageNode alone has no effect.  
**Fix:** Add PlayMontageChainNode to graph, or use PlayMontageNode for single playback.

#### ANIM009: ReleaseLookNode without prior LookAt
**Rule:** ReleaseLookNode appears in execution path without LookAtPointNode or LookAtEntityNode → **WARNING**  
**Rationale:** ReleaseLookNode blends out aim; if aim is not active, call is a no-op.  
**Fix:** Add a LookAtPointNode or LookAtEntityNode before ReleaseLookNode, or remove ReleaseLookNode if not needed.

#### ANIM010: Span-cast mutation safety (bytecode validation)
**Rule:** Codegen uses `MemoryMarshal.Cast<AnimationMontageQueue, AnimationMontageQueueEntry>` pattern without GCHandle → **ERROR**  
**Validation Method:**
- IL scanning: Detect Span.AsBytes + MemoryMarshal.Cast sequence
- Verify no unsafe patterns (direct pointers, ref.Equals on Span result)
- Verify mutation lifetime is within pinned scope

**Reference Pattern** (safe):
```csharp
ref var queue = ref repo.GetComponentRW<AnimationMontageQueue>(entity);
var span = MemoryMarshal.Cast<AnimationMontageQueue, AnimationMontageQueueEntry>(
    MemoryMarshal.AsBytes(new Span<AnimationMontageQueue>(ref queue))
);
// Mutations on span are safe within this scope
```

#### ANIM011: Cross-subsystem context validation
**Rule:** Validates that all Phase 5 nodes are safe for use in BTree, HSM, and Blueprint Instance contexts → **ERROR**  
**Checks:**
1. Node type is registered with all three dispatchers (AnimationDispatcher for Blueprint Instance, BTreeEvaluator, HsmActionExecutor)
2. Output connections (for getter nodes) are properly typed
3. Input entity references (TargetCharacter) are valid in Blueprint context

**Scope:** Phase 5 Part 2 nodes (5 new + 6 from Part 1 = 11 total) all verified safe.

## Developer Insights

### Q1: Getter Node Output Types (Tuple vs Component Fields)
**Decision:** Use separate Blueprint output ports (not tuple/record).  
**Rationale:**
- Blueprint ports are typed individually (uint, float) → cleaner visual representation
- Tuple returns would require unpacking in graph → extra nodes
- Separate ports enable partial connections (e.g., use CurrentStance but ignore BlendWeight)
- Consistent with GetMontageQueueProgressNode 3-port pattern

**Implementation:**
- GetMontageQueueProgressNode has 3 output ports: CurrentEntryIndex, ElapsedSeconds, TotalCount (all uint except ES)
- GetCurrentStanceNode has 2 output ports: CurrentStance (uint), BlendWeight (float)
- Blueprint compiler introspection automatically discovers output count from node reflection

### Q2: Look-at Executor Entity Resolution Timing
**Timing:** Resolution happens at **executor dispatch time** (per-tick in LookAtDispatcherSystem), not at compile time.

**Rationale:**
- TargetCharacter is a uint entity ID → may be invalid/destroyed at runtime
- LookAtDispatcherSystem checks entity validity before executor allocation (DD-4 §4)
- Invalid entity → silent no-op (consistent with PlayMontageNode pattern)
- This allows safe "aim at stored entity ID" patterns where ID may become stale

**Implementation Detail:**
- LookAtPointNode and LookAtEntityNode both start with `public uint TargetCharacter;`
- Dispatcher reads `node.TargetCharacter`, validates entity exists in repo
- If valid: creates executor with world-space target (point or entity+offset)
- If invalid: skips executor, LookAtChannel remains in previous state

### Q3: ANIM009 Sequencing Validation (Execution Path Tracing)
**Challenge:** How does validator detect if LookAtPointNode and ReleaseLookNode are in sequence?

**Answer:** **Static execution path analysis** on Blueprint DAG:
1. Graph traversal from Entry node follows all possible paths (breadth-first)
2. For each path containing ReleaseLookNode, check if path also contains LookAtPointNode or LookAtEntityNode
3. If ReleaseLookNode reachable without prior LookAt → warning

**Example (Valid):**
```
Entry → LookAtPointNode → Sequence → ReleaseLookNode → Exit
```
Validator sees both nodes on same path → OK

**Example (Invalid):**
```
Entry → Selector 
  ├─ Branch A: LookAtPointNode → ... (maybe doesn't execute)
  └─ Branch B: ReleaseLookNode → Exit (executes without LookAt)
```
Validator warns: "ReleaseLookNode may execute without LookAt in Selector Branch B"

### Q4: ANIM010 Bytecode Verification (IL Scanning vs AST)
**Approach:** **IL scanning** (not AST) for maximum robustness.

**Rationale:**
- Codegen may optimize differently across C# versions / JIT modes
- IL is runtime-stable and reflects actual memory access patterns
- AST analysis cannot detect inlining, constant folding, ref-folding optimizations

**Verification Steps:**
1. **Extract IL** from codegen'd EnqueueMontageNode executor method using System.Reflection.Emit
2. **Pattern match** for:
   - `ldarg` (load entity ref) → `ldflda` (load field address) → `dup` (duplicate for both AsBytes + mutation)
   - `call MemoryMarshal.AsBytes` → `call IAsyncStateMachine.MoveNext()` (check no GCHandle between)
3. **Reject patterns** with:
   - `ldfld` + pointer arithmetic (direct memory access)
   - `call ref.Equals` on Span result
   - `call Span.GetPinnableReference()` without `pinvoke`

**Trade-off:** IL scanning is heavier than AST but catches actual runtime safety issues.

### Q6: Cross-subsystem Dispatch Surprises
**Surprise 1: Enum Normalization**
- Animation subsystem uses `enum StanceId { Standing, Crouched, Prone }`
- Blueprint compiler must coerce to `uint` for output port type
- Discovered: Reflection-based port discovery auto-converts enum→uint (no custom handling needed)

**Surprise 2: Entity Reference Validity**
- GetCurrentStanceNode and LookAtNodes both read `TargetCharacter: uint`
- Assumed: Entity must be in same EntityRepository as executor
- Discovered: Dispatcher must validate `repo.HasEntity(targetEntityId)` before executor call
- Missing validation causes silent no-op (no exception) → easy to miss in testing

**Surprise 3: Offset Floating-Point Precision**
- LookAtEntityNode has 3 offset fields (X, Y, Z as float)
- Test case: offset = 0.5 (head height)
- Assumed: Exact match in underwater/ragdoll scenarios
- Discovered: Aim executor applies offset *after* distance check → offset can cause aim-out-of-range
- Solution: Offset should be small relative to animation distance (≤ 1.0 unit recommended)
