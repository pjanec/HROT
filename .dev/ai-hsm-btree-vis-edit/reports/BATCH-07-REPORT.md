## Issues encountered

### 1. `PackResult` positional record — breaking parameter insertion

`PackResult` is a positional (primary-constructor) record. Inserting `TotalHeavyBytes` as
a third positional parameter shifted all subsequent parameters. All three call sites
(`Pack()` itself and the overload, plus `BuildViewModel`) had to be updated simultaneously.

**Resolution:** Updated all sites in a single pass. Test suite caught any missed sites.

### 2. `file sealed class` constraint in test file

`MutableBbAssetForWindowTests` is declared as `file sealed class` inside the test file.
C# forbids using a file-local type as a return type or parameter type of any non-file-local
method. An attempt to extract a `CreateAsset()` helper method failed with CS9051.

**Resolution:** Each test method instantiates `MutableBbAssetForWindowTests` directly
with `new MutableBbAssetForWindowTests(...)`. No shared helper needed; the duplication
is acceptable given the small number of fields.

### 3. Wrong marker text in `EmitHeavy` tests

Initial `EmitHeavy_produces_correct_marker_block` test asserted
`Assert.Contains("// <auto-generated>", output)` — that marker does not exist in this
codebase. The actual marker is `FluentCSharpEmitterBase.EditorGeneratedMarker`
(`// HROT_EDITOR_GENERATED - ...`).

**Resolution:** Changed the assertion to use `FluentCSharpEmitterBase.EditorGeneratedMarker`
directly. This also makes the test resilient to future marker text changes.

### 4. Over-broad `DoesNotContain("public ", ...)` assertion

`EmitHeavy_empty_heavy_fields_produces_empty_struct` asserted
`Assert.DoesNotContain("public ", output)`. This failed because the struct declaration
itself (`public partial struct Empty_Heavy`) contains "public ". The intent was to
assert that no field declarations are present.

**Resolution:** Replaced with `Assert.DoesNotContain("public int", output)` and
`Assert.DoesNotContain("public float", output)`, which specifically check for field
declarations rather than the keyword in any context.

## Weak points spotted

1. **`PackResult` positional record** — positional records are fragile: adding any
   property in the middle is a breaking change. For records with more than three fields
   that are likely to evolve, named init-only properties would be safer. Recorded in
   DEBT-TRACKER.md.

2. **`EmitHeavy` always emits usings based on `model.Fields`**, not filtered to only
   the fields that are actually heavy. If the caller passes a pre-filtered model (all
   heavy fields), this is correct. But the contract is implicit — the caller must do
   the filtering. A more defensive design would accept the full model plus a `HashSet<string>`
   of heavy field names, or a `PackResult`. Fine for now, but worth noting.

3. **"Promote to new variable" right-click menu item** in the unbound requirements
   section is a stub (no action). This is intentional per the instructions (Phase 1.5d),
   but the deferred action should be tracked.

## Design decisions made beyond the spec

1. **`BudgetColor()` helper extracted** — The budget-bar color logic (white / amber / red
   based on percentage) is the same for both inline and heavy tiers. Extracted into a
   private static `BudgetColor(int used, int budget)` helper method rather than inlining
   the threshold checks twice. Thresholds: <80% white, >=80% amber, >=100% red.

2. **Unbound requirements section always visible** — The spec said "always-visible for
   discoverability". The section renders even when `UnboundRequirements.Count == 0`,
   showing only the "UNBOUND SUB-TREE REQUIREMENTS" header (collapsed by default when
   empty). This makes it clear to designers where requirements would appear.

3. **`Repack` sorts by alignment descending (capped at `AlignmentCap`)** — The spec said
   "largest-alignment-first". The cap at `AlignmentCap` (which is already applied in
   `SizeOf`) prevents pathological sorts from large structs with unknown alignment from
   dominating the sort order.
